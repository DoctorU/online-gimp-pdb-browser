# Phase 0: Existing Browser and Catalog Baseline

## Purpose

Phase 0 records the implementation that already exists before the planned
procedure-extraction work in Phase 1. It is a description of the current
baseline, not a claim that every built-in GIMP procedure family is covered.

The project already has a static online browser and a production
catalog-generation pipeline. Phase 1 should build on this foundation rather
than treat the website or all catalog generation as unimplemented.

## A. Production website and catalog

### Production catalog generation

The Pages workflow at
[`pages.yml`](../../.github/workflows/pages.yml) generates and deploys the
production site. It runs
[`scripts/build_pdb.py`](../../scripts/build_pdb.py) against a GIMP source
checkout, passing both the Script-Fu source directory and the native
`app/pdb` C source directory.

- **Script-Fu Scheme:** the Python builder reads `.scm` files, recognizes the
  `script-fu-register` and `script-fu-register-filter` forms, and associates
  `script-fu-menu-register` menu paths with procedures.
- **Native PDB C:** the same Python builder parses C files under `app/pdb`,
  looking for `gimp_procedure_new` registrations and related static procedure
  name, help, attribution, argument, and return-value calls. This is static
  source parsing; it does not run or intercept those C registration calls.

The generated JSON is sorted by procedure name and records the GIMP source
revision, generation timestamp, source repository, procedure metadata,
parameters, return values, and source links. The published catalog contains
native PDB procedures in the `gimp-*` namespace, such as `gimp-file-load`,
extracted from `app/pdb`, and Script-Fu procedures. It does not contain C
plug-in procedures such as `file-png-load`, which is registered by the
separate PNG file plug-in.

The catalog does not include built-in C plug-in registrations or Python
plug-in registrations. Its published procedure names are the `gimp-*` native
PDB family and Script-Fu records; it does not include C plug-in names such as
`file-png-load`. The Script-Fu parser handles only the registration forms
listed above; it is not a general Script-Fu interpreter or complete parser
for every registration API.

At verification on 2026-10-18, the published JSON contained 858 records:
802 `gimp-*` entries with kind `native-pdb`, and 56 entries with kind
`script-fu` (55 named `script-fu-*` and the test procedure `test7`). The
catalog was generated from GIMP source revision
`bc819b5a927562d21e52f0977589fde74f271463`.

### Production browser and deployment

[`index.html`](../../index.html), [`app.js`](../../app.js), and
[`styles.css`](../../styles.css) make up a static browser that loads
`data/pdb.json` in the visitor's web browser. It provides:

- A searchable, alphabetically grouped procedure list.
- A detail view with the fields supported by the current catalog, including
  descriptions, attribution, menu location, parameters, return values for
  native procedures, and links to the corresponding GIMP source revision.
- Local preview through Python's standard HTTP server; visitors do not need
  to install or run GIMP to browse a published catalog.

The current interface has separate presentation paths for `native-pdb` and
Script-Fu records. It does not yet present metadata from C plug-ins or Python
plug-ins because those records are not generated by the current builder.

The workflow runs on pushes to `main`, manual dispatch, matching rebuild
tags, and a daily schedule. It fetches the GIMP source repository's default
branch, assembles the static site, and deploys it to GitHub Pages.

The workflow currently does not select the latest stable GIMP 3 release
explicitly, compare stable revisions before building, or validate catalog
schema and coverage before deployment. Its recorded source commit provides
provenance, but the current update policy is not yet the program's intended
stable-release policy.

For a local preview of the generated catalog:

```sh
python3 -m http.server 8000
```

Open <http://localhost:8000> from the repository root. To regenerate the
existing catalog, use the build instructions in the [README](../../README.md).

## B. Experimental and proof-of-concept work

### Existing Python live-PDB exporter

[`scripts/capture_pdb_poc.py`](../../scripts/capture_pdb_poc.py) is a separate
Python proof of concept. It runs inside GIMP through the Python batch
interpreter, queries the PDB after GIMP has loaded procedures, and serializes
the metadata exposed by those live procedure objects.

This experiment is not used by the Pages production workflow. It does not scan
C source code and does not intercept plug-in registration calls. A procedure
such as `file-png-load` will appear in its export only if that plug-in is
available and has registered the procedure in the GIMP instance used for the
query.

### Proposed Python-assisted C registration collector

A different, not-yet-implemented experiment is to compile or run C plug-in
registration code against a lightweight collector/stub and use Python to
record or serialize the observed registrations. This is intended to
investigate C plug-in registration behavior, not to query the already-loaded
live PDB. The feasibility and boundary of such a collector remain open; it is
not production code and is not part of the current site-generation pipeline.

The native `app/pdb` source parser in `build_pdb.py` is also distinct from
this proposed collector: it statically parses source declarations and already
contributes native entries to the production catalog.

## Current coverage and limitations

| Procedure family | Current baseline |
|------------------|------------------|
| Native `app/pdb` C | Included in production via static source parsing; not runtime registration capture. |
| Built-in C plug-ins | Not included in the production catalog. |
| Built-in Python plug-ins | Not included in the production catalog. |
| Script-Fu | Selected Scheme registration forms are extracted; parser coverage is limited to implemented forms. |
| Third-party plug-ins | Not included. |

The generated catalog describes what the source-based builder recognizes. It
does not prove that every record is exposed by a running GIMP, nor does it
capture registrations that depend on runtime conditions. The current
workflow also does not enforce a completeness threshold or protect
publication with schema and coverage gates.

## Relationship to Phase 1

Phase 1 begins from the production browser and catalog described in section A.
It should build on the native `app/pdb` entries already generated through
static Python-based source parsing, while investigating how to cover
built-in C plug-in registrations reliably. The existing live-PDB exporter and
the proposed registration collector in section B are separate experiments;
neither should be confused with the production source-based pipeline. See
the [Phase 1 plan](./phase1.md) for the planned extraction and validation
work.
